================================================================================
INTERVIEW PREPARATION NOTES: GYMNI
(Multi-Agent Fitness Coach Bot: Strava + Hevy -> Telegram)
================================================================================

1. ONE-PARAGRAPH SUMMARY
Gymni is an automated, multi-agent personal fitness coaching bot that integrates 
Strava and Hevy workout data with Telegram to provide immediate, unprompted post-workout 
analysis and hold interactive 30-minute coaching conversations. Triggered asynchronously 
via webhooks whenever a workout completes, Gymni parses weight training exercises, 
sets, and reps directly from Strava's activity descriptions (eliminating the need 
for a paid Hevy Pro API) and extracts second-by-second telemetry streams for endurance 
runs. To prevent AI hallucinations, all mathematical operations—including training 
volume, estimated 1RM, personal records (PRs), heart rate zones, aerobic decoupling, 
and acute:chronic workload ratios (ACWR)—are calculated deterministically in pure 
Python by a Data Agent. Google Gemini LLM agents are strictly confined to qualitative 
interpretation, motivational coaching, and selecting from 22 pre-built Matplotlib 
chart presets before delivering formatted rich media back to the user's Telegram chat.
Source: README.md; Gymni_PRD.md §1-§2; DECISIONS.md.

2. ARCHITECTURE
Gymni is built as a serverless event-driven architecture with clear separation between 
fast webhook ingestion, durable queue dispatch, analytical agents, and client rendering:

1. Webhook Ingestion Layer:
   - Job: Authenticates incoming webhooks, deduplicates events, enqueues tasks to QStash, 
     and immediately returns HTTP 200 (well within provider timeouts).
   - Inputs: Strava webhook events (aspect_type="create", object_id); Telegram updates.
   - Outputs: Immediate HTTP 200 responses (<200 ms); tasks enqueued to Upstash QStash.
   - Files: app/web/strava_webhook.py, app/web/telegram_webhook.py, api/index.py.

2. Worker Orchestration & Pipeline (The Brain):
   - Job: Consumes webhook tasks dispatched by QStash, fetches fresh upstream data, 
     and orchestrates agent execution.
   - Inputs: QStash HTTP POST requests containing verified event payloads.
   - Outputs: Dispatches tasks to Data Agent, specialized analysts, and chart renderers.
   - Files: app/web/worker.py (WorkerDeps, _handle_strava_activity, _handle_conversation_turn).

3. Analytical Agent Layer:
   - Job: Multi-agent coordination: classifies user requests, computes metrics deterministically, 
     generates domain-specific insights (strength/endurance), and chooses visualizations.
   - Inputs: Normalized workout records, historical database context, user chat messages.
   - Outputs: Pre-computed metrics dictionaries, qualitative insight text, chart preset selections.
   - Files: app/agents/orchestrator.py (OrchestratorAgent), app/agents/data_agent.py 
     (pure Python), app/agents/strength_analyst.py (StrengthAnalystAgent), 
     app/agents/endurance_analyst.py (EnduranceAnalystAgent), app/agents/chart_agent.py 
     (ChartAgent), app/agents/conversation.py (ConversationAgent).

4. Data & State Storage Layer:
   - Job: Persists relational activity history, sets, PRs, and profiles in Postgres, 
     while maintaining conversational session memory and deduplication locks in Redis.
   - Inputs: Structured exercise records, user profile data, session context.
   - Outputs: Historical PR comparisons, weekly aggregate stats, active conversation turns.
   - Files: app/storage/repositories.py, app/storage/session_memory.py, 
     app/storage/redis_lock.py, app/storage/event_log.py.

5. Rendering & Client Integration Layer:
   - Job: Renders selected chart presets into in-memory PNGs using Matplotlib and formats 
     analyst text into Telegram-compliant HTML/Markdown.
   - Inputs: Chart preset IDs, pre-computed data arrays, raw LLM commentary.
   - Outputs: BytesIO image streams; Telegram sendMessage and sendPhoto API payloads.
   - Files: app/render/telegram.py (TelegramRenderer), app/charts/theme.py, 
     app/charts/strength.py, app/charts/endurance.py, app/charts/cross.py, 
     app/clients/telegram.py (TelegramClient).

3. TECH STACK AND WHY
- Python 3.11: Chosen for modern typing, dataclasses, asynchronous support, and 
  access to rich scientific libraries (NumPy, Matplotlib) and official AI SDKs. 
  Source: pyproject.toml; .python-version.
- Vercel Serverless (Python Runtime): Selected as the primary cloud hosting platform 
  because Netlify Functions do not natively support Python (Netlify only supports 
  JS/TS/Go). Vercel provides native Python serverless execution with 0.3-1s cold starts, 
  comfortably meeting webhook deadlines. Source: Gymni_PRD.md §0.2; vercel.json.
- Google Gemini 1.5 Pro / Flash (Google GenAI SDK): Selected for low-latency, 
  structured JSON output support (response_schema) and cost-effective multi-turn 
  conversational reasoning. Source: app/clients/gemini.py; Gymni_PRD.md §7.
- PostgreSQL (Neon / Supabase): Serves as the relational source of truth for 
  activity metadata, individual lifting sets, historical PR records, and athlete profiles, 
  queried via connection pooling (psycopg). Source: migrations/001_init.sql; Gymni_PRD.md §4.
- Upstash Redis: Serverless in-memory store used for distributed deduplication locks 
  (SETNX with TTL) and holding 30-minute conversation session memory. Source: 
  app/storage/session_memory.py; app/storage/redis_lock.py.
- Upstash QStash: Serverless HTTP queue that decouples synchronous webhook responses 
  from asynchronous worker execution, guaranteeing retries with exponential backoff 
  without managing worker infrastructure. Source: app/storage/queue.py; Gymni_PRD.md §3.1.
- Matplotlib & NumPy: Chosen for deterministic, local server-side chart rendering 
  into in-memory BytesIO buffers, ensuring zero LLM code execution risk. 
  Source: app/charts/theme.py; app/charts/strength.py.
- Cryptography (Fernet): Encrypts sensitive Strava OAuth access and refresh tokens 
  at rest in the PostgreSQL database using symmetric Fernet encryption. 
  Source: app/security/crypto.py (TokenCipher).

4. KEY DESIGN DECISIONS
1. Parsing Strava Descriptions Instead of Integrating the Hevy API:
   - Decision: Rather than requiring a paid Hevy Pro subscription and implementing 
     the Hevy API client, Gymni parses the freeform set/rep text that Hevy writes 
     into Strava's activity description upon syncing.
   - Trade-off: Requires maintaining a specialized regex parser (app/parsers/hevy_strava_description.py) 
     and a local muscle-group dictionary (app/metrics/muscle_mapping.json), but saves 
     the user a paid monthly subscription and collapses the dual-trigger sync problem.
   - Code: DECISIONS.md (2026-07-26 entry); app/parsers/hevy_strava_description.py.

2. Complete Separation of Math (Data Agent) and Language (Gemini):
   - Decision: The LLM is strictly prohibited from calculating numbers. All arithmetic 
     (volume, e1RM, heart rate zones, ACWR) is computed by pure Python functions in 
     the Data Agent.
   - Trade-off: Requires writing and testing extensive Python metric functions and 
     data schemas, but completely eliminates arithmetic hallucinations and unit errors.
   - Code: README.md; app/agents/data_agent.py; app/metrics/strength.py; app/metrics/endurance.py.

3. Asynchronous Webhook Offloading via QStash:
   - Decision: Webhook handlers perform zero heavy lifting; they only validate auth, 
     deduplicate, push to QStash, and return HTTP 200 immediately.
   - Trade-off: Adds an external queue dependency (QStash), but ensures responses 
     comfortably beat Strava's strict 2-second timeout and Telegram's retry threshold.
   - Code: app/web/strava_webhook.py; app/storage/queue.py.

4. 22 Locked-Down Chart Presets over LLM Code Generation:
   - Decision: Chart generation uses 22 pre-coded Matplotlib functions. The Chart Agent 
     LLM only selects a preset ID (e.g., s01) and simple parameters.
   - Trade-off: Limits visual layouts to pre-authored templates, but guarantees 100% 
     visual consistency, dark-mode styling, and zero risk of arbitrary code execution.
   - Code: app/charts/strength.py; app/charts/endurance.py; Gymni_PRD.md §6.2.

5. Fernet Token Encryption at Rest:
   - Decision: OAuth access and refresh tokens are encrypted using Fernet symmetric 
     keys before being stored in PostgreSQL.
   - Trade-off: Requires key management via FERNET_KEY environment variable, but 
     guarantees that a database snapshot compromise does not leak full Strava account access.
   - Code: app/security/crypto.py (TokenCipher); migrations/001_init.sql.

6. PROJECT-SPECIFIC DETAILS
- List of Agents and Their Roles:
  1. OrchestratorAgent (Gemini): The conversational and workflow router. In multi-turn 
     chat, classifies user questions and determines which data fields must be queried 
     from Postgres (app/agents/orchestrator.py).
  2. DataAgent (Pure Python): Non-LLM computational engine. Queries database history 
     and computes all quantitative metrics: total tonnage, set intensities, estimated 
     1RMs, PR detection, heart rate zone boundaries, and ACWR (app/agents/data_agent.py).
  3. StrengthAnalystAgent (Gemini): Domain coach for resistance training. Ingests 
     pre-computed strength metrics and writes qualitative analysis focusing on progressive 
     overload, volume balance, and recovery needs (app/agents/strength_analyst.py).
  4. EnduranceAnalystAgent (Gemini): Domain coach for running and cardio. Evaluates 
     pacing splits, aerobic decoupling (cardiac drift), cadence, and elevation efficiency 
     (app/agents/endurance_analyst.py).
  5. ChartAgent (Gemini): Visual director. Analyzes session metrics and selects the 
     single most insightful chart preset ID (e.g., s01 for volume, e01 for HR zones) 
     from the 22 pre-coded templates (app/agents/chart_agent.py).
  6. ConversationAgent (Gemini): Follow-up dialog agent. Answers user questions during 
     the 30-minute active post-workout window using pre-fetched data (app/agents/conversation.py).

- Trace One Telegram Message Step by Step:
  1. The user types "/pr Bench Press" or asks "How was my chest volume this week?" in Telegram.
  2. Telegram's Bot API sends an HTTP POST update to Gymni's /api/webhook/telegram endpoint.
  3. telegram_webhook.py verifies the X-Telegram-Bot-Api-Secret-Token header and checks 
     if the sender matches owner_chat_id.
  4. The webhook enqueues the update payload to Upstash QStash and returns HTTP 200 (<200 ms).
  5. QStash delivers the payload to /api/worker.
  6. worker.py verifies the QStash JWT signature and loads the active session state 
     from Redis (SessionMemory).
  7. OrchestratorAgent classifies the user's intent and outputs structured data requirements 
     (e.g., fetch PR history for Bench Press).
  8. DataAgent executes parameterized SQL queries against Postgres to retrieve the requested numbers.
  9. ConversationAgent generates a coaching response grounded strictly in the fetched data.
  10. TelegramRenderer formats the response into Telegram Markdown/HTML, and TelegramClient 
      invokes sendMessage to reply directly in the chat.

- Trace One Strava Webhook Step by Step:
  1. The user finishes a workout; Hevy syncs the session to Strava.
  2. Strava sends an HTTP POST event to /api/webhook/strava with aspect_type="create" 
     and object_id=12345678.
  3. strava_webhook.py computes event_hash = sha256(owner_id:object_id:create) and 
     checks Upstash Redis (SETNX strava:dedup:{event_hash}, ex=86400).
  4. If new, the webhook enqueues the task to QStash and immediately returns HTTP 200.
  5. QStash calls /api/worker. The worker acquires a Redis execution lock (worker:lock:12345678).
  6. StravaClient decrypts the user's OAuth token via TokenCipher and fetches the full 
     activity JSON and telemetry streams from Strava API.
  7. If weight training, hevy_strava_description.py parses exercises, sets, reps, and 
     weights from the description.
  8. DataAgent computes total volume, estimated 1RMs, and compares against Postgres 
     history to flag new PRs.
  9. StrengthAnalystAgent (or EnduranceAnalystAgent) generates coaching commentary.
  10. ChartAgent inspects the highlights and selects a preset (e.g., s01_volume_by_muscle).
  11. Matplotlib renders the chart into an in-memory BytesIO PNG.
  12. TelegramRenderer compiles the message, and TelegramClient sends both the chart 
      photo and coaching text to the user's Telegram.

- QStash and Redis Deduplication Flow:
  - Upstash QStash: Acts as an external serverless queue. Webhook endpoints offload 
    tasks to QStash via an authenticated REST call, returning 200 OK instantly. 
    QStash handles retries with exponential backoff if the worker fails.
  - Redis Deduplication:
    - Webhook Level: When Strava retries or fires duplicate webhooks, strava_webhook.py 
      checks Redis key strava:dedup:{event_hash}. If the key already exists, it returns 
      200 OK immediately without enqueuing.
    - Worker Level: Redis distributed lock worker:lock:{activity_id} prevents race 
      conditions if duplicate jobs are processed simultaneously.

- How Metrics Are Computed and Why Gemini Only Interprets Them:
  - Volume: Sum of (weight_kg * reps) across completed working sets (warmups excluded).
  - Estimated 1RM: Calculated using the Epley formula: weight * (1 + reps / 30), or 
    the Brzycki formula for low rep counts: weight * (36 / (37 - reps)).
  - PRs: Current top weight and calculated 1RM are compared against historical max 
    records in the personal_records Postgres table.
  - Aerobic Decoupling: Divides the run into halves; computes (Pace / HR)_half1 vs 
    (Pace / HR)_half2 to measure cardiac drift percentage.
  - ACWR: Computes acute load (last 7 days total volume) divided by chronic load 
    (last 28 days weekly average load).
  - Why Gemini Only Interprets: LLMs are prone to arithmetic errors, hallucinated PRs, 
    and calculation drift. Computing all metrics in deterministic, unit-tested Python 
    guarantees mathematical accuracy. Gemini receives clean JSON dictionaries in system 
    prompts and is restricted to qualitative narrative synthesis.
  Source: app/metrics/strength.py; app/metrics/endurance.py; README.md.

- Database Tables and Redis Contents:
  - PostgreSQL (9 tables defined in migrations/001_init.sql & 002):
    1. activities: Strava activity metadata (id, name, type, start_date, moving_time, distance, calories).
    2. exercise_sets: Individual lifting sets parsed from descriptions (activity_id, exercise_name, muscle_group, set_index, weight_kg, reps, rpe).
    3. personal_records: Historical record achievements per exercise (exercise_name, pr_type, value, achieved_at).
    4. user_profile: Athlete physiological baselines (max_hr, resting_hr, lthr, bodyweight_kg).
    5. oauth_tokens: Encrypted Strava OAuth credentials (access_token, refresh_token, expires_at).
    6. learned_exercise_muscles: Dynamic lookup table mapping exercise names to muscle groups.
    7. lap_records: Split and lap intervals for runs.
    8. stream_samples: Second-by-second telemetry points (time, hr, cadence, velocity).
    9. event_logs: Processed event hashes ensuring idempotency.
  - Upstash Redis Contents:
    - strava:dedup:{event_hash}: 24-hour deduplication keys for webhook events.
    - session:{chat_id}: JSON-serialized list of conversational turns maintaining the 30-minute context window.
    - worker:lock:{activity_id}: Temporary distributed execution locks.

7. HARDEST PROBLEMS
1. Gemini Structured Output Schema Rejection in Orchestrator:
   - Problem: In production, the OrchestratorAgent failed silently on every single turn, 
     always falling back to "no data needed."
   - Fix: Investigating raw API responses revealed that Gemini's Developer API 
     structured-output mode (response_mime_type="application/json") strictly rejects 
     Pydantic schemas containing dict[str, str] fields with a 400 Bad Request. 
     Refactored the orchestrator's response schema to use explicit list-of-objects 
     (list[DataRequirement]) instead of freeform dictionaries.
   - Lesson: Cloud LLM structured-output compilers have strict schema limitations; 
     always test with strict Pydantic primitives rather than dynamic dict types.
   - Source: DECISIONS.md (2026-07-26 CORRECTION); NEXT_SESSION.md.

2. Hardcoded Empty Conversation Data Context:
   - Problem: Even after fixing the orchestrator's schema, conversational turns still 
     responded with generic statements, claiming no access to the user's PRs or workout stats.
   - Fix: Discovered that _handle_conversation_turn in worker.py was hardcoding an empty 
     fetched_data_json="{}" regardless of what data requirements the orchestrator outputted. 
     Wired the orchestrator's output directly into DataAgent database query methods, 
     populating the conversation agent with real PR and volume records.
   - Lesson: Multi-agent pipelines require end-to-end integration tests that verify 
     data actually traverses the boundary between intent classification and context injection.
   - Source: DECISIONS.md; NEXT_SESSION.md.

3. Hevy Sync Description Parsing Quirks:
   - Problem: Hevy's auto-generated Strava descriptions contain unpredictable markdown 
     formatting, custom emojis, warm-up set prefixes ("- Set 1: ..."), drop sets, 
     and failure notes that broke naive line splitters.
   - Fix: Built a resilient regex-based state machine in app/parsers/hevy_strava_description.py, 
     backed by real-world fixture regression tests in tests/test_parser_real_fixtures.py, 
     handling non-standard characters, imperial-to-metric conversions, and unmapped exercises.
   - Lesson: When relying on third-party user-facing sync descriptions as an API alternative, 
     parsers must be built around extensive real-world snapshot fixtures.
   - Source: DECISIONS.md; app/parsers/hevy_strava_description.py.

9. INTERVIEW QUESTIONS & ANSWERS (First Person "I")
Q1: What is the core problem Gymni solves?
A1: Most fitness apps provide raw workout logs or generic AI advice, but they either 
require manual data entry or suffer from calculation hallucinations. I built Gymni as 
an automated personal coach that listens to Strava webhooks, parses workout data without 
requiring paid API subscriptions, calculates all physiological metrics in pure Python, 
and delivers personalized, unprompted analysis to Telegram within minutes of finishing a session.

Q2: Why did you decide not to use the official Hevy API?
A2: The official Hevy API requires a paid Hevy Pro subscription, creating unnecessary 
friction and cost for the user. I discovered that when Hevy syncs to Strava, it writes 
structured set and rep details directly into Strava's activity description. By building 
a robust regex parser to extract workout data from that description, I collapsed our 
data pipeline into a single Strava trigger and saved the user a paid subscription.

Q3: How do you prevent Gemini from hallucinating mathematical calculations like 1RM and PRs?
A3: I enforced an architectural rule separating calculation from interpretation: the LLM 
is never allowed to perform math. Our Python Data Agent computes total volume, estimated 
1RMs using Epley equations, PR comparisons, and heart rate zone distributions. These 
verified numbers are serialized into clean JSON and passed to Gemini strictly for qualitative 
synthesis and coaching advice.

Q4: How do the webhook endpoints beat Strava's strict 2-second timeout?
A4: Our webhook handlers perform zero analytical or database processing. When a Strava 
event arrives, the handler performs constant-time token verification, checks an in-memory 
Redis key to discard duplicate events, pushes the payload to an Upstash QStash queue, 
and returns an HTTP 200 response in under 200 milliseconds. All heavyweight API fetching 
and agent reasoning happen asynchronously in our worker.

Q5: Why did you choose Vercel over Netlify for hosting?
A5: During project discovery, I identified that Netlify Functions only support JavaScript, 
TypeScript, and Go runtimes—Python on Netlify exists solely as a build tool, not as a 
request handler. Since our core data agents, Matplotlib charting, and scientific libraries 
are written in Python, I selected Vercel Serverless, which provides native Python runtime 
support with sub-second cold starts.

Q6: How do the chart presets work and why don't you let the LLM generate code?
A6: Letting an LLM generate plotting code introduces latency, syntax errors, and arbitrary 
code execution vulnerabilities. Instead, I pre-built 22 locked-down Matplotlib chart 
presets covering volume distributions, heart rate zones, and ACWR trends. The Chart Agent 
LLM only selects a preset ID like s01 based on session highlights, and our local engine 
renders the image deterministically into an in-memory PNG buffer.

Q7: What was the bug that caused the Orchestrator agent to fail silently?
A7: When testing multi-turn conversations, our orchestrator consistently fell back to 
"no data needed" because Gemini's Developer API structured-output compiler strictly 
rejects Pydantic schemas containing dict[str, str] fields with a 400 error. I resolved 
this by refactoring the response schema into explicit list-of-objects structures, which 
Gemini compiles reliably.

Q8: How do you secure user credentials and OAuth tokens?
A8: Strava OAuth access and refresh tokens are encrypted at rest in our PostgreSQL database 
using symmetric Fernet encryption (TokenCipher). All webhook secrets and API keys are 
compared using constant-time hmac.compare_digest to prevent timing attacks, and our logging 
pipeline includes regex filters that redact bot tokens before writing log lines.

Q9: What is ACWR and how is it used in your endurance coaching?
A9: ACWR stands for Acute:Chronic Workload Ratio. It compares an athlete's acute training 
load over the last 7 days against their chronic rolling average over the last 28 days. 
In our cross-training agent, an ACWR between 0.8 and 1.3 is flagged as the progressive 
training "sweet spot," while a ratio exceeding 1.5 triggers an automated recovery alert 
warning the athlete of elevated injury risk.

Q10: What role does Upstash Redis play in Gymni?
A10: Redis serves two vital operational roles: first, it provides short-lived distributed 
locks and 24-hour event deduplication keys to ensure webhook retries don't trigger duplicate 
coaching messages. Second, it holds the 30-minute conversational session state (SessionMemory), 
allowing the user to ask follow-up questions about their recent workout without storing 
ephemeral chat history in PostgreSQL.

Q11: How do you detect Personal Records (PRs) across different exercise variants?
A11: When lifting sets are parsed, the Data Agent queries the personal_records table 
for the highest historical weight and calculated 1RM for that specific exercise. If any 
set in the current workout exceeds the recorded benchmark, the Data Agent flags it as a 
new PR, updates the database, and injects a celebration directive into the Strength 
Analyst's prompt.

Q12: If you had another month to work on Gymni, what would you add?
A12: I would implement multi-tenant authentication so multiple athletes could connect 
their own Strava accounts, and I would add support for Telegram voice memos using OpenAI 
Whisper, allowing users to speak their workout feedback during rest periods and receive 
spoken audio coaching in response.

coaching architecture that connects Strava, Hevy, and Telegram while enforcing strict 
mathematical integrity.

When an athlete completes a workout, Strava fires a webhook. To comfortably beat Strava's 
strict 2-second timeout, our serverless webhook handler verifies the request, checks an 
in-memory Redis deduplication key, pushes the job to an Upstash QStash queue, and returns 
an HTTP 200 in under 200 milliseconds. 

When the worker executes, our Python client decrypts the user's Strava tokens using Fernet 
encryption and fetches the activity. One of our key architectural decisions was parsing 
the workout description that Hevy automatically syncs to Strava, which saved the user 
from paying for a Hevy Pro subscription. 

The heart of the system is the complete decoupling of calculation from language. Our 
pure-Python Data Agent calculates all quantitative metrics: total volume, estimated 1RMs 
using Epley equations, all-time PR detection, heart rate zone splits, and acute:chronic 
workload ratios. These verified numbers are passed to specialized Gemini agents: a Strength 
Analyst for lifting, an Endurance Analyst for runs, and a Chart Agent that selects the single 
best visual preset from 22 pre-coded Matplotlib templates. 

The final analysis and custom chart are delivered to Telegram within a minute of finishing 
the workout, and our conversation agent maintains a 30-minute interactive sliding window 
in Redis so the athlete can ask follow-up questions. The entire project is backed by 197 
automated unit tests, ensuring robust parsing, encryption, and multi-agent coordination."
